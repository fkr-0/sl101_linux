# SL101 0076: A/B of the kernel switch `disable_auto_dont_kmap` (2026-11-09)

Question: is the automatic GEM `DONT_KMAP` for V1 buffers above 256 KiB
(`!want_kmap && size > SZ_256K` in `drivers/gpu/drm/grate/gem.c`) necessary for the
first-use buffer corruption (docs/sl101-0075-256k-extended-review-20261109.md)?

## Setup (what actually ran)

* Device `.106` (CID 035344534c31323880ac79a543010300), kernel
  `7.0.1-postmarketos-grate-k76`: pristine pmOS source (commit bfffc6d6, APKBUILD SHA512
  verified) + `kernel-auto-dont-kmap-v1-safe.patch`, built on the host with its OWN module
  tree under a distinct release. Booted via APX -> RAM U-Boot -> SD extlinux (autoboot).
* Library: Debian chroot installed 87e071dc (prod73), probe `0075-bo-256k-v2.armhf`
  (SHA df6ba486...), the 0075 coordinator with only the kernel pin changed
  (`ab-k76/run-v2-k76.sh`, `supervisor-probe-k76.py`; originals untouched).
* Driver `ab-k76/ab-run.sh`: sets `/sys/module/tegra_drm/parameters/disable_auto_dont_kmap`,
  reads it back before and after every trial, stops on any deviation, restores `N` at the end.
* Source texture 512x513 L8 (262656 B, above 256 KiB), 854x480 target, flag mode `observe`
  (no userspace flag forcing). Kernel messages: 0 in all 71 trials.

## Results (evidence in `work/.../ab-k76/evidence/`, `analyze_ab.py`)

| Run | param N (stock behaviour) | param Y (auto DONT_KMAP off) |
|---|---:|---:|
| 30-trial run (blocks+solid, 513) | 4/15 corrupt | 0/9 |
| 40-trial run, order N N Y Y x10 | 9/20 corrupt | 0/20 |
| All 513 observe trials | 13/36 corrupt | 0/29 |

One-sided Fisher exact: 40-run p = 6.1e-4, all trials p = 1.4e-4. Corruption is absent in the
first 16 trials of the 40-run (also with N) and present from trial 17; inside that active
stretch N is 9/12 and Y 0/12 (p = 1.7e-4). Positive control (forced DONT_KMAP at 512 rows,
param N): 1/3 corrupt; 512 rows with Y: 0/3 (not informative at that n).

## Conclusion and limits

* With the switch off no corrupt frame appeared in 29 trials in which the stock path corrupts
  36 %. Within one boot, same kernel, the automatic DONT_KMAP of buffers above 256 KiB is
  necessary for the corruption seen here (512x513 source, 854x480 target).
* Not proven: why (cache, zeroing, GART, TEX read), whether other fresh-BO corruption
  (e.g. the 640x360 copy destination in the 216-case matrix) disappears too, or whether the
  switch has side effects (kernel address space for large BOs). The corruption has an
  on/off regime over time (first 16 trials clean) that we did not control.
* This is a diagnostic result, not an installed fix. The proper options are an explicit
  workaround (default-off heuristic, measured for memory cost) or the actual fix of the
  no-kernel-mapping allocation path.

* A cold boot does not read `/boot/extlinux/extlinux.conf`; it only applies after APX. The
  extlinux menu is unusable (no input device), hence `timeout 1` autoboot
  (`directboot-plan/stage_extlinux.py`: `autoboot-experimental`, `default-restore`,
  `rollback`). Staging is still active; a power-cycle returns to the stock kernel.
* Reproduce the numbers: `python3 work/sl101-0076-dontkmap-kernel-20261109/ab-k76/analyze_ab.py`

## Hypothesis from the source and handoff to the remap experiment kernel

Not proven; written down so the next kernel is tested with the same tooling.

* CORRECTION (verified in `kernel-src`): an earlier version of this section claimed the ARM32
  build does not use `kernel/dma/direct.c`. That was wrong. `dma_direct_alloc()` tests
  `DMA_ATTR_NO_KERNEL_MAPPING` FIRST and returns `dma_direct_alloc_no_mapping()` before the
  `arch_dma_alloc()` dispatch (`ARCH_HAS_DMA_ALLOC=y`, ARM `__dma_alloc`/CMA path). So a
  `DONT_KMAP` BO takes the dma-direct path: `__dma_direct_alloc_pages(..., gfp & ~__GFP_ZERO)`
  (not zeroed), and `arch_dma_prep_coherent()` ("remove any dirty cache lines on the kernel
  alias") is a no-op because `ARCH_HAS_DMA_PREP_COHERENT` is not selected on ARM. Only
  allocations WITH a kernel mapping reach ARM `__alloc_from_contiguous`, which zeroes and
  flushes (L1+outer) and calls `__dma_remap`. Hence a fresh `DONT_KMAP` BO contains the previous
  user's data and may have dirty cache lines on its cacheable lowmem alias that are written back
  over GPU data later - matching the first-use-only, 32-byte-line, wrong-value findings.
* Note for patch review (`work/sl101-prod-dma-init-20261110/patches/0002`): it zeroes through
  `kmap_local_page` and calls `arch_sync_dma_for_device(..., DMA_TO_DEVICE)`. On ARM v7 that is
  clean only (`v7_dma_map_area` -> `v7_dma_clean_range`, `outer_clean_range`); lines stay valid.
  `__dma_clear_buffer` uses clean+invalidate (`dmac_flush_range`/`outer_flush_range`).
  Whether clean-only suffices must be measured; a flush variant is the safer equivalent of the
  missing `arch_dma_prep_coherent`.
* Open: the prefill test showed WRONG VALUES written by the GPU, which fits a dirty/stale
  cached alias being written back over GPU data better than a pure stale CPU read.
* Experiment kernel (built by another agent): keep NO_KERNEL_MAPPING, remap lowmem attributes
  symmetrically and restore on free. Recommended design for a clean test: gate the remap behind
  its own runtime module parameter (default off, applies to newly allocated BOs) so ONE boot can
  run the ABBA matrix stock-vs-remap with `disable_auto_dont_kmap` as the known-clean control;
  rates differ between boots, so cross-boot comparisons are weak.
* Reuse: `ab-k76/make-release-copies.sh RELEASE OUTDIR` re-pins the device scripts
  (`ab-run.sh`, `ab-bo-run.sh`, coordinator/supervisor/mount-restore copies, plans) to another
  `7.0.1-postmarketos-grate-<suffix>` release (it refuses the stock release and existing
  dirs). Always base device copies on the HOST lane files (the device copy of
  `coordinator-bo-run.sh` still pinned the old installed SHA). Browser must not run during a
  matrix (qualification lock).
* Only one lane may change `.106`'s graphics state or boot it; the experiment kernel needs a
  new APX boot by the operator (`directboot-plan/stage_extlinux.py`, `apx-uboot-k76.sh`).

| Run | Condition | Corrupt first-use cases |
|---|---|---:|
| 216 cases, plan `plan-bo-216-abba.txt` (the column for the k76 parameter is ignored) | fresh boot (3-17 min uptime, 224 MB page cache) | **0/216** (all sizes 0/72, all variants 0/36, all blocks 0) |
| 108 cases (first 6 blocks) after a page-cache churn | cache 794 MB, CMA pool 256 MB almost empty (0.4 MB free at start) | **0/108** |

Reference (k76 kernel, same cases, one boot): stock path 38/108 corrupt, automatic DONT_KMAP off
0/108 (docs above). With the stock rate the chance of 0/216 is about 2e-41; 95 % upper bound on
the dmafix1 rate with 0/216 is 1.7 %. Kernel messages 0 in all 324 cases.

Reading: zeroing the pages of a `DMA_ATTR_NO_KERNEL_MAPPING` allocation in `dma_direct_alloc_no_mapping`
and syncing them (patch 0002) removes the first-use corruption in this matrix while keeping the
automatic DONT_KMAP heuristic. This supports the mechanism (fresh unzeroed pages with stale
cache lines on the lowmem alias) and gives a candidate fix.

Limits: different boot than the k76 numbers (cross-boot comparison; the stock path was clean in
some early trials of other boots); 324 cases, one unit, one memory regime family; not yet tested
across reboots, with video playback or Cog, or with a clean-vs-flush variant. Not installed as the
production kernel; production deployment of a patched package kernel (APKBUILD patch, own rebuild,
backup/rollback, physical access) is a separate gate. Cost: the patch zeroes every
NO_KERNEL_MAPPING buffer (a few MiB each), which is the same cost the mapped path already pays.
